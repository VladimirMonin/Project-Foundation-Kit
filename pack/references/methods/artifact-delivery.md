# Проверка конкретной поставки

## Когда нужен метод

Когда заказаны архив, пакет, bundle, Release asset или другая проверяемая передача.
Не добавлять выпуск к каждой правке, EXE к библиотеке, backend к визуальному каталогу
или установку в рабочий профиль к переносимому комплекту. Конечная форма и адресат
определяются заказом; эта справка не разрешает сборку, сеть, публикацию или установку.
Принимать по [lifecycle](../lifecycle.md), выбирать evidence и безопасную изоляцию по
[quality](../quality.md). Не создавать второй release-процесс, реестр или evaluator.

## Условный маршрут

1. **Определить контракт передачи.** Назвать результат, адресата, конечную форму,
   обязательные проверки и разрешённые переходы. Patch, wheel, onedir, web-сборка,
   редактируемый дизайн и переносимый Markdown-пакет — разные объекты. Для PFK это
   весь согласованный переносимый состав, включая ресурсы и обязательные лицензии,
   не только отдельный SKILL.md. Незаданные переходы не достраивать автоматически.
2. **Связать принятый кандидат с build inputs.** Указать точную принятую редакцию
   либо ограниченный набор путей/байтов, значимые зависимости, build config и способ
   упаковки. До сборки сверить реальные входы с принятыми: commit, Git blob, index и
   рабочие байты могут различаться, в том числе из-за EOL. Соседние чужие изменения
   не включать. Не требовать чистоты всего checkout при независимой работе, но все
   значимые входы выбранного кандидата должны быть определены и стабильны.
3. **Идентифицировать фактический комплект.** Проверить полный набор передаваемых
   файлов, ожидаемые и лишние members, ресурсы, metadata и необходимые notices;
   зафиксировать идентификатор итоговых байтов, например SHA-256. Для onedir объект —
   весь каталог, а не вынутый EXE. Для архива — сам архив и его распакованный состав.
   Один номер версии, успешная сборка или hash главного файла не подтверждают
   комплектность. Hash связывает байты, не доказывает правильность или авторство.
4. **Проверить нужную форму у потребителя.** В разрешённой отдельной области выполнить
   реальный вход поставки вне богатого исходного дерева: полезный сценарий, readback
   результата и существенный отказ. Для установленной библиотеки проверить настоящий
   consumer и происхождение загруженных модулей, не только импорт/`--help`/JSON parse.
   Для bundle — нужную ветку с динамическими модулями и ресурсами. Для переносимого
   документального набора — состав, ссылки и заявленный инструмент из перенесённой
   папки, если инструмент входит в заказ; это статическая, не продуктовая приёмка.
   Для визуального каталога — редактируемость и рендер выбранных состояний, не backend.
   Перенос в другую папку проверяет relocation, но сам не доказывает «чистую машину».
5. **Сохранить и передать только разрешённое.** Следовать существующим владельцам
   приёмки/index/release. Сверить сохранённые байты с принятым кандидатом; после push
   прочитать точный целевой remote ref и commit, не подменять main feature-веткой
   или tag-ом. Для заказанного Release проверить его состояние, адрес и точные assets;
   после передачи скачать/прочитать фактический файл или комплект у адресата и
   сравнить с ожидаемым составом/байтами. Успех write API или push сам не readback.
6. **Проверить установленное состояние, только если оно заказано.** Установленный
   entrypoint и загруженные ресурсы должны относиться к переданной поставке.
   Существующий старый EXE не обновляется исправлением source рядом. Проверка
   отдельной среды не означает смену рабочего профиля, глобальных настроек или
   установку другим потребителям. Назвать фактически проверенную среду и границу.

## Разные состояния, не одна галочка

| Установленный факт | Чего он ещё не доказывает |
|---|---|
| Автор передал кандидат и checks | Независимой приёмки, если она требуется местной политикой |
| Кандидат принят в указанной области | Что нужные байты вошли в commit или сборку |
| Пакет построен и идентифицирован | Что полезный путь исполняется в форме поставки |
| Локальный commit содержит принятую дельту | Что целевой remote ref обновлён |
| Remote ref содержит ожидаемый commit | Что опубликован нужный Release asset |
| Файл у адресата совпадает с ожидаемым | Что он установлен или выбран реальным entrypoint |
| Установленный путь проверен | Все платформы, права, зависимости и будущие версии |

Строки выбираются по заказу; это не обязательная цепочка стадий. Авторская проверка
и независимая приёмка остаются разными действиями по существующей политике, без
добавочного reviewer-а. CI относится к своему commit/config; отсутствие checks —
NOT_RUN, не зелёная CI. Успешный отрицательный тест не означает успех операции.

## Изменение после проверки и окончание

После изменения исходников, dependency inputs, build config, package data или
входящей в пакет документации оценить impact. Изменившийся пакет получает новую
идентичность и связь с evidence; старый PASS не переносится на него автоматически.
Неизменённые поведенческие результаты можно переиспользовать с основанием; внешние
записи и дорогие проверки не повторяются ради комментария без существенной причины.
Повторная сборка не равна побайтно воспроизводимой сборке, если это отдельно не обещано.

Достаточный итог в существующей [форме проверки](../../templates/documents/verification.md.tmpl)
или задаче: точный объект/входы, реальные commands/exits и наблюдения, свежие и
переиспользованные evidence раздельно, фактические переходы передачи, обязательный
остаток/owner либо конец. NOT_RUN обязательной ветки остаётся открытым; условия вне
согласованной области ограничивают вывод, но не становятся новым поручением.
Не публиковать полное environment, секреты, личные данные или сырые журналы ради
provenance. Неизвестное обозначать явно, не восполнять правдоподобным результатом.
