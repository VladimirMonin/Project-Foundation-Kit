## FigCraft: от знакомства с инструментом до законченной работы 🧭

Этот комплект объединяет техническое руководство, два практических кейса, методическую статью и рабочее приложение. Материалы отвечают на разные вопросы: что доступно в редакторе, что удалось проверить на практике, какой объём дизайна нужен конкретной задаче и как передать результат следующему исполнителю.

Серия рассчитана на работу с ИИ-агентами, однако её основные принципы применимы и к обычной команде. Редактируемый документ помогает согласовать внешний вид; описание состояний связывает его с поведением; реализация в целевом приложении подтверждает работу настоящих элементов управления и операций.

### Главный методический акцент 🎯

**Редактируемый визуальный эталон может быть самостоятельным законченным заказом.** Такой результат определяет композицию, компоненты, оформление, тексты, необходимые состояния и правила изменения размеров. Его ценность состоит в том, что следующему исполнителю больше не приходится угадывать визуальные решения.

Интерактивность выбирается отдельно. Один проект требует проверить последовательность действий, другой — сравнить несколько подготовленных состояний, третий — согласовать только внешний вид нового раздела. Возможность добавить переход в FigCraft сама по себе не делает этот переход обязательным пунктом каждого заказа.

Работу настоящего интерфейса проверяют в целевом приложении: там действуют его контролы, обработчики, локальное состояние, фоновые операции и связь с ядром. Известное поведение можно описать и сохранить при переносе. Воспроизведение всей этой системы внутри макета требуется только при соответствующей цели прототипирования.

Наблюдение за изменениями документа остаётся полезным при любой глубине: оно позволяет увидеть результат работы агента, сравнить варианты и своевременно уточнить решение. Полная имитация приложения для этого не обязательна.

| Воссоздать существующий интерфейс как визуальный эталон | Часть III: цель и границы → часть II, кейс A → профильные разделы части I → формы практического приложения. |
| Создать новый GUI поверх готового ядра | Часть III: разделение работ → часть II, кейс B → раздел целевой технологии в части I → практическое приложение. |
| Проверить неоднозначное взаимодействие до реализации | Часть III: выбор глубины → часть II, раздел о живом прототипе → ограниченное задание из практического приложения. |

Последовательное чтение всего комплекта полезно для изучения подхода. Для проектной работы достаточно выбранного маршрута: разделы про другие технологии и неподходящие виды проверки не становятся дополнительными обязательствами.

### Как применять ранние перечни проверок 🔎

В первых двух частях рассматривается широкий набор возможностей и проверок. Он применяется к **заказанному результату**, а не целиком к каждому макету. Проверка структуры нужна для заявления о редактируемых компонентах; проверка живого перехода — для заявления о работающем переходе; проверка файловой операции — для соответствующей функции приложения.

Уточнение цели не превращает прежний неудачный эксперимент в успешный. Если переход не работал, наблюдение сохраняет силу. При новом заказе на визуальный эталон этот переход может оказаться за его пределами, но такая смена границ должна быть названа прямо. Аналогично изложенный в части III метод — предложение организации работы, а не доказательство уже завершённого проекта или измеренной экономии времени.

Эти даты определяют границы материалов. Описанная версия не объявляется последней на момент любого будущего чтения. Успешный отдельный сценарий также не подтверждает все возможности редактора. Для Qt серия рассматривает перенос спецификации и ресурсов в целевой интерфейс; автоматическое получение готового PySide6/PyQt6-приложения не обещается.

### Открытие и навигация по файлам 🗂️

Все ссылки этого указателя относительные. После распаковки файлы следует хранить в одной папке с исходными именами; тогда переходы между материалами сохранятся.

Документы используют Markdown, таблицы, диаграммы Mermaid и выноски формата Obsidian. В Obsidian они отображаются непосредственно; в других редакторах результат зависит от поддержки этих расширений. Диаграмма или выноска, показанная как текст, остаётся читаемой частью исходного документа. Команды и примеры кода в статьях служат материалом для конкретной задачи и требуют соответствия её технологии, версии и разрешённому объёму работ.
