# pf-quality

## Когда применять и когда нет

Используй при подготовке существенного изменения, исправлении бага, изменении
контракта, теста или диагностического выхода. Помоги адаптировать
[стратегию тестирования](../../templates/foundation/testing-strategy.md.tmpl) и
[политику наблюдаемости](../../templates/foundation/observability-policy.md.tmpl),
если их действительно нет. Не заменяй существующую принятую стратегию шаблоном.
Не запускай полный suite, сеть, реальные устройства или дорогую зависимость только
потому, что навык доступен. Для обычной правки ссылки достаточно проверки ссылки.

## Вход

Действующие правила и профиль проекта; сценарий/баг и ожидаемый результат;
изменённые owners и потребители; доступные тесты/команды; разрешённые данные,
расходы и выходные каналы; относящееся прежнее evidence. Непроверенная команда —
не «рабочая команда проекта». Начни с [общих правил качества](../../references/quality.md).

## Порядок

1. Сопоставь сценарий с владельцем, успешным исходом, существенным отказом и
   инвариантом сохранности. Найди существующую проверку; не строй второй продукт
   в helper или новый test harness ради локального контракта.
2. Выбери минимальную границу доказательства: unit, integration, сценарий через
   реальный путь приложения, при необходимости E2E/installed/native/visual.
   Назови заменённые внешние зависимости. Coverage и линтер не доказывают
   пользовательский результат или правильность архитектуры.
   Если обещан живой процесс, выбери значимые промежуточные наблюдения и управляемый
   порядок событий; финальный успех не доказывает прогресс, раннюю отмену или cleanup.
   Для визуального эталона оцени выбранные состояния/рендер, не требуй исполнения backend.
3. До import/collection/config access проверь ранние побочные эффекты и настрой
   disposable data/cache/log/temp roots. Доступ к рабочим секретам не нужен для
   synthetic-теста. При отказе partial setup освобождает только свои ресурсы.
4. Выполни разрешённую адресную проверку по
   [инструкции тестирования](../../templates/instructions/testing.md.tmpl).
   Если запуска нет — запиши проект проверки и честный NOT_RUN, не PASS.
   Различай дефект приложения, oracle/fixture, тестовых данных и окружения;
   raw failure сохраняется, повторный успех не объясняет причину.
   Запиши, какая ветка реально достигнута: ранний отказ не испытывает позднюю защиту.
   Исполнение/утверждение проверки, исход операции и готовность передачи — разные оси
   по quality. Ожидаемый ненулевой product exit может дать PASS теста; внешний exit0
   helper-а не перекрывает вложенный failure, skip или неизвестный эффект.
5. Для изменённой диагностики следуй
   [инструкции логирования](../../templates/instructions/logging.md.tmpl): проверь
   фактический handler output, полезные технические факты, unknown vs zero и
   отсутствие synthetic секретов/содержимого. Локальный сбор, DEV и внешняя
   отправка требуют разных разрешений.
6. Оцени применимость прежнего результата по owners, условиям, fixture, версии
   и артефакту. Повтори только затронутые/непроверенные случаи. Обнови затронутое
   устойчивое знание; передай один краткий итог по
   [местной политике приёмки](../../references/lifecycle.md#владелец-приёмки-и-повторных-проверок),
   без нового контура review.

## Адресные методы

Для конкретного бага — [поведенческая регрессия](../../references/methods/behavior-regression.md):
требование, выбранный runner-ом и достигнутый путь, содержательный RED, минимальная
разрешённая коррекция и тот же GREEN. Ошибка collection/dependency не RED продукта.
Тест должен отвергать конкретный неверный исход; непустой field-кейс и empty-кейс
различаются, sandbox-only не доказывает parity.

Для общего формата/значимых consumers сверяй [actual impact](../../references/methods/change-impact.md)
с правильной базой и всей относящейся дельтой, а не только чистотой рабочего дерева.
Для изменённой границы используй [тот же канон контракта](../../references/methods/contract-evolution.md):
настоящая сериализация, consumer и connected path; четыре слоя не четыре обязательных
инструмента. Не читай все методы при обычной правке ссылки.

Для живой связи GUI/исполнения выбирай только затронутые случаи
[05, §23 — временные границы](../../references/architecture/command-first/05_Command_First_Live_GUI_Backend.md#testing)
и [07, §10–11 — расписание и lifetime](../../references/architecture/command-first/07_Command_First_Verification_and_Delivery.md#concurrency):
первый элемент готов при работающем втором, A приходит после B, отмена до handle,
результат до cleanup, отказ наблюдателя после эффекта. Фиксируй достигнутую границу;
барьер управляет временем настоящего пути, а не подставляет готовый результат.
Для позднего сбоя/partial используй
[07, §13 — точки эффекта](../../references/architecture/command-first/07_Command_First_Verification_and_Delivery.md#effects)
и семантику отдельного эффекта из метода контрактов.

Если заказан пакет, bundle, Release или иная передача, используй
[artifact-delivery](../../references/methods/artifact-delivery.md): квалифицировать
конкретные байты нужной формы, затем проверить только согласованные переходы доставки.
Это не требование установить приложение или повторить прежний внешний write ради текста.

## Результат и остановка

Достаточная карта «риск → проверка → наблюдение», фактические команды/raw exits,
подмены и границы, необходимая регрессия и конкретный остаток. Написанное,
статически прочитанное, выполненное, skipped, cancelled, UNREACHED и подтверждённый
пользовательский путь различаются. Достигнуты согласованные критерии — остановись;
не создавай дополнительную проверку проверяющего.

Неизвестен важный контракт или право на данные/вызов — один точный вопрос owner-у.
Остальные безопасные независимые проверки продолжай. Для технического неизвестного
найди только относящийся owner/API и конечный факт; не начинай аудит всей системы.

## Примеры

**Правильно:** экспорт выбирает неверный слой. Сравнить разные synthetic raw/processed
значения через реальный export owner, прочитать выход, проверить сохранность при
отказе. Внешний дорогой provider не нужен. Назвать ровно этот путь подтверждённым.

**Неправильно:** после изменения подписи запустить все live-проверки, получить
skips и объявить продукт готовым по покрытию; либо убрать failing assertion.

Формат навыка: [Agent Skills specification](https://agentskills.io/specification).
Навык не изменяет права, не запускает подагентов и переносится только с целым пакетом.
