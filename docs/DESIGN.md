# Устройство Project Foundation Kit

## Назначение

Переносимый методический комплект для инженерных решений, проверки поведения, сопровождения знаний и проектирования интерфейсов; не runtime framework и не оркестратор агентов. UI — осознанное ограниченное расширение редакции 0.2.0, не универсальное разрешение реализовывать продукт. Переносится содержимое всего `pack/`, обычно в `tools/project-foundation/`. Адаптированные документы принадлежат принимающему проекту и не заменяются автоматически при обновлении комплекта.

## Разделение ответственности

- `pack/skills/` — семь процедур применения: pf-bootstrap, pf-plan, pf-maintain, pf-quality, pf-guides, pf-ui-design, pf-command-first. UI-вход имеет web/React и desktop/PySide6 приложения и условный маршрут FigCraft. Архитектурный вход отделяет прикладные операции от адаптеров. Каждый навык использует относительные ссылки на общие ресурсы.
- `pack/references/lifecycle.md` — соразмерность изменений, сопровождение знания, приёмка и завершение.
- `pack/references/metadata.md` — единственный словарь свойств, типов документов и статусов; связи переводов и исключения для нативных форматов.
- `pack/references/quality.md` — достаточность доказательств, уровни проверки и безопасная диагностика.
- `pack/templates/` — выбираемые формы, не автоматически принятые документы. `{{field_name}}` заполняет автор или агент; это не универсальные переменные Obsidian.
- `pack/integrations/` — способы использования клиентами с явными границами обнаружения и загрузки.
- `pack/tools/` — небольшой read-only checker, его закреплённая зависимость и контракт.
- `tests/` — тесты и синтетические проекты, не пользовательские приложения.

Основание объясняет причины и компромиссы, инструкция задаёт действия, шаблон предоставляет форму, навык организует применение. Общие правила не должны расходиться между семью навыками. Три условных метода внутри существующих входов уточняют эволюцию контрактов, actual impact и содержательную регрессию, не создавая registry/evaluator. Формы не обязательны по числу; роли могут быть разделами одного документа.

## Библиотека знаний 0.3.0

В [command-first](../pack/references/architecture/command-first/README.md) входят пять
оригинальных документов; [руководство FigCraft](../pack/references/ui/figcraft/FigCraft_AI_GUI_Design_Guide_RU.md)
добавлено целиком. Имена, содержимое, собственные YAML-шапки и ссылки сохранены
побайтно. Это native-справка, не заполненные принятые заметки по схеме PFK.
Родной формат не получает вторую схему; контрольные суммы и происхождение принадлежат
[UPSTREAM](../pack/UPSTREAM.md). Корневой `.gitattributes` исключает преобразование
концов строк только этих шести снимков при Git checkout.

Короткие pf-command-first и FigCraft-маршрут выбирают нужные разделы, не пересказывают
всю библиотеку. Контракты и паспорта используют существующие формы; очереди, IPC,
общая сессия и MCP появляются по требованиям, не автоматически. FigCraft MCP управляет
дизайн-редактором и не является MCP будущего продукта. Практическую квалификацию новой
методики на реальной разработке выполняет пользователь, отдельно от выпуска документов.

## Границы адаптации

Сначала учитывать существующие правила, владельцев и расположение документов. Создавать только нужные наполненные документы. Различать текущее поведение, предложение, предположение и исполненную проверку. Повтор без необходимой дельты должен быть no-op без изменения дат.

Использовать обычные относительные Markdown-ссылки. Перед сохранением заполненного шаблона удалить служебные подсказки и пересчитать ссылки от конечного расположения. Нативные AGENTS/SKILL и заполненные заметки имеют разные схемы.
